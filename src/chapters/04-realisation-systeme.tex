\chapter{R\'ealisation du syst\`eme}
\label{chap:realisation}

\section{Introduction}

Le prototype associe un paquet Python pour l'apprentissage, une API FastAPI et
une interface React. Il s'exécute localement ou avec Docker Compose. Ce chapitre
explique le rôle des outils, le traitement d'une observation et les écrans
utilisés pour examiner les résultats.

\section{Environnement de d\'eveloppement}

\subsection{Environnement mat\'eriel}

La station sur laquelle le projet est disponible dispose d'un processeur
Intel Core i5-10400F à six cœurs et douze fils d'exécution, avec environ
16~Go de mémoire vive, sous Arch Linux 64 bits. Cette configuration a été
relevée le 9 septembre 2026. Le code d'apprentissage utilise des modèles
Scikit-learn exécutés sur le processeur et ne requiert pas de GPU.

Ce relevé décrit le poste actuel. Les caractéristiques de la machine n'ayant
pas été enregistrées avec les mesures de latence, il ne permet pas à lui seul
de reconstituer les conditions matérielles de ces mesures.

\subsection{Environnement logiciel}

Neovim (\texttt{nvim}) a servi à l'édition du code. Le carnet Jupyter regroupe
l'exploration du jeu de données et les comparaisons des modèles. Les
environnements Python sont gérés avec \texttt{uv}, tandis que \texttt{npm}
installe les dépendances de l'interface React et lance ses tests. Docker
Compose réunit les services pour les essais d'intégration et les
démonstrations.

Le relev\'e du 7 septembre 2026 enregistre Python 3.12.13, Node.js 26.8.0 et le
noyau \texttt{Linux 7.1.9-arch1-2}. Le tableau~\ref{tab:software-environment}

\section{Organisation de la r\'ealisation}

Le code est réparti entre l'apprentissage, le backend et le frontend. Cette
organisation permet de modifier les traitements ou les écrans séparément,
tant que le format des données échangées reste compatible.

\begin{description}
  \item[Apprentissage automatique.] Le paquet \texttt{iot\_ids\_ml} prépare
  les données, entraîne les modèles et compare leurs résultats. Les modèles
  retenus sont enregistrés avec un manifeste qui contient les empreintes des
  fichiers et les références du rapport d'évaluation.

  \item[Backend.] L'application FastAPI reçoit les observations, vérifie
  leur format et donne accès aux prédictions et aux alertes. Les travaux en
  attente et leur historique sont conservés en base afin de reprendre un
  traitement interrompu. L'outbox conserve les messages à diffuser après
  l'enregistrement des résultats.

  \item[Frontend.] L'application React propose des espaces consacrés à la
  supervision, aux alertes, aux modèles, aux observations et à la topologie.
  Le module \texttt{api.ts} centralise les échanges avec le serveur pour que
  les composants se concentrent sur l'affichage et les actions de l'utilisateur.
\end{description}

\section{Principaux choix d'impl\'ementation}

\subsection{Du modèle entraîné à la prédiction servie}

Pour chaque observation, le détecteur décide d'abord si le flux est normal
ou suspect. Seuls les flux classés comme attaques passent au classifieur de
familles. Avant d'utiliser les modèles, le registre vérifie leur schéma,
l'ordre des variables et les empreintes des fichiers. Un fichier incompatible
avec le manifeste actif est refusé.

Le même ordre de 83 variables est contrôlé à l'entraînement et à l'inférence.
Le rejeu permet d'exercer cette chaîne avec les données enregistrées sans
réentraîner le modèle. La liste \texttt{top\_features} renvoyée avec une
prédiction classe cinq valeurs d'entrée selon leur magnitude absolue; elle ne
mesure pas leur influence sur le modèle. Pour les alertes ML compatibles avec
les versions actives, un point d'accès distinct calcule à la demande des
contributions SHAP \citep{lundberg_unified_2017}. Dans le cas des modèles
calibrés, ces contributions expliquent la marge de l'estimateur arborescent
ajusté du premier pli de calibration, et non la probabilité calibrée. Elles
aident à lire une prédiction, sans établir les causes d'une attaque.

\subsection{Ingestion durable et traitement des erreurs}

L'ingestion HTTP valide un lot complet avant toute insertion. L'identifiant
d'\'ev\'enement et l'empreinte du contenu assurent l'idempotence. Le travailleur
r\'eserve ensuite un travail, ex\'ecute la cascade et valide dans une transaction
l'observation, la pr\'ediction, l'alerte \'eventuelle, la transition et les
messages d'outbox. La diffusion temps r\'eel ne commence qu'apr\`es cette
validation.

Une nouvelle soumission identique n'ajoute pas une seconde observation ; un
contenu différent sous le même identifiant est refusé. Après une erreur
temporaire, le travail est repris avec un délai et un nombre d'essais bornés.
Les échecs persistants passent en état \texttt{dead\_letter}. Une relance
manuelle authentifiée est disponible pour les travaux encore compatibles avec
la route de modèle active; le motif et la nouvelle transition sont conservés.

\subsection{Interface, contrôle d'accès et provenance}

Les indicateurs de l'interface ne portent pas tous sur les mêmes données.
Certains résument l'historique enregistré en base, d'autres concernent les
alertes chargées ou les événements reçus depuis l'ouverture du navigateur.
Leur périmètre est indiqué pour que ces valeurs puissent être interprétées
correctement.

La session opérateur utilise un jeton à durée limitée ; l'interface traite
son expiration et les refus de l'API. L'identité associée à une qualification
provient du jeton validé, et non d'un nom libre fourni par le navigateur.
Les vues présentent les états de chargement, d'erreur et de reconnexion pour
éviter qu'une donnée ancienne soit confondue avec un état actualisé.

Dans le laboratoire, Suricata observe le trafic MQTT et HTTP du réseau Docker
isolé. L'agent transmet les événements avec une identité machine distincte.
L'interface affiche leur origine de signature ; ils ne traversent pas la cascade
RT-IoT2022. NFStream reste une voie d'extraction PCAP hors ligne distincte.

\subsection{Exécution reproductible}

Pour retrouver rapidement un environnement coh\'erent, les commandes courantes
ont \'et\'e regroup\'ees dans le Makefile. \texttt{make setup} installe les
d\'ependances et \texttt{make verify-model} contr\^ole que les mod\`eles charg\'es
correspondent bien à leur manifeste. La commande \texttt{make demo} crée une
base SQLite temporaire, puis lance par l'API le rejeu d'un nombre configurable
d'observations normales et d'attaque en proportions égales.
\texttt{make demo-sensor} démarre un environnement complet distinct, comprenant
le laboratoire Suricata. Les scripts appliquent les migrations et vérifient
la disponibilité des services au démarrage.

\section{Validation technique}

La validation combine des tests des traitements individuels et des essais
de l'application complète. Les tests Python couvrent la préparation des données,
les mod\`eles, l'API, la persistance et l'ingestion. Vitest contr\^ole les
adaptateurs et les composants React, tandis que Playwright reproduit dans un
navigateur les actions principales d'un op\'erateur. Les commandes \texttt{make
test}, \texttt{make lint}, \texttt{make build} et \texttt{make
project-preflight} rassemblent ces contr\^oles avant une d\'emonstration.

Les tests Storybook exercent les interactions des composants isolés. D'autres
contrôles comparent les chiffres du support de soutenance au rapport d'évaluation.
Le fichier \path{machine-learning/reports/generated/presentation-evidence.json}
enregistre une répétition terminée le 7 septembre 2026 : les trois groupes de
vérifications (projet, déploiement Docker temporaire et laboratoire Suricata)
portent le statut \texttt{pass}. Le journal du projet rapporte dix parcours
navigateur réussis; celui du laboratoire vérifie trois scénarios de signature.
Ces résultats décrivent cette exécution locale. Ils ne mesurent pas la qualité
de détection sur un réseau externe.

\section{Difficultés rencontrées et solutions apportées}

Trois difficultés ont particulièrement marqué le travail : comprendre les
données, fixer une limite aux expérimentations et rendre le tableau de bord
facile à lire.

\subsection{Comprendre les caractéristiques du jeu de données}

Au début du projet, la principale difficulté était de comprendre ce que
représentaient les variables de RT-IoT2022. Il était possible de lancer un
entraînement sans pour autant savoir interpréter une durée de flux, un compteur
de paquets ou une mesure calculée dans un sens de communication. L'étude de la
description du jeu de données et l'exploration dans Jupyter ont aidé à relier
ces caractéristiques au trafic observé. L'examen des distributions, des valeurs
égales à zéro et des doublons a également permis de mieux comprendre les données avant
de comparer les modèles.

\subsection{Savoir quand passer des essais à l'application}

La comparaison des modèles pouvait facilement se prolonger : chaque résultat
donnait envie d'essayer un autre réglage. Il fallait pourtant avancer sur
l'application. Le protocole présenté au chapitre~\ref{chap:resultats} a donné
un cadre à cette étape : comparer quatre familles sur les mêmes partitions,
retenir les modèles selon leur macro-F1 de validation et réserver le test à
l'évaluation finale. Cette règle a permis de fixer une version de référence
pour l'intégration, tout en conservant les autres essais pour l'analyse.

\subsection{Rendre le tableau de bord compréhensible}

Les premières versions du tableau de bord affichaient beaucoup de chiffres,
mais il n'était pas évident de savoir lesquels regarder en premier. La mise en
page a donc été reprise plusieurs fois. Les vues actuelles séparent la
supervision, l'investigation des alertes et l'analyse des modèles. Cette
organisation permet de commencer par une vue d'ensemble, puis de consulter les
détails utiles à une question précise. Le travail sur les libellés et sur la
distinction entre historique enregistré et activité de la session a également
aidé à clarifier la lecture des indicateurs.

\section{Conclusion}

Le prototype permet de soumettre une observation, d'enregistrer sa prédiction
et d'examiner l'alerte correspondante. Les journaux de la répétition documentent
le fonctionnement des parcours applicatifs et du laboratoire. Le chapitre
suivant examine une autre question : les erreurs commises par les modèles sur
les données de test.
